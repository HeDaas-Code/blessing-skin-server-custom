# Faction layout grammar

Apply this matrix on every invocation. A faction is not allowed to inherit a universal “left list + center stage + right action” dashboard merely because the content fits.

Low-confidence spatial profiles are provisional, but their context corrections and non-interchangeable topology stay fixed.

## Variation contract

At `moderate` depth and above, the selected faction must differ from the other profiles in at least three of:

- dominant axis: horizontal, vertical, diagonal, radial, or layered;
- navigation position and topology;
- main stage proportion and location;
- decision region position;
- relationship between primary and secondary instruments;
- overlap, inset, edge docking, or negative-space behavior.

Do not count palette, typography, texture, border radius, or icon choice as layout variation.

## Task adaptation

- Keep the profile’s spatial relationship while adapting its content. A Rhine Lab route task may still use an instrument-dominant bench; it does not need to copy Lungmen’s map shell.
- If the task lacks enough information for every region, collapse a region into its owner instead of filling it with decorative cards.
- Shared application controls may occupy a neutral global bar. Faction-owned navigation and decisions must use the selected spatial profile.
- On portrait widths, preserve reading order and ownership rather than the desktop coordinates. Convert a wrap, lintel, or edge dock into an equivalent top strip, bottom strip, or disclosure.

## Layout collision test

Compare the selected screen with all other faction profiles at the same depth:

1. Blur the text and remove color.
2. Check the dominant axis, navigation position, stage proportion, and decision position.
3. Reject the layout if it can become another faction by swapping labels and tokens.
4. Reject repeated three-column shells unless the selected profile explicitly owns one and the neighboring profiles do not.
